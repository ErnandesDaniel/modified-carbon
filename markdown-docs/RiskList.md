# 2. Risks (Риски)

## 2.1 R1: Технический долг и снижение качества кода

### 2.1.1 Risk Magnitude or Ranking (Вероятность появления и серьезность)

Вероятность: Высокая. Серьёзность: Средняя. Тип риска: Разработка. Порог: покрытие тестами < 30%.

В условиях жёсткого дедлайна (4 месяца) и малой команды (2 разработчика) возникает соблазн сокращать рефакторинг, пропускать code review и писать «быстрые» решения. Технический долг накапливается, что замедляет разработку в поздних итерациях и увеличивает количество дефектов.

### 2.1.2 Description (Описание)

Накопление неоптимального кода, пропуск рефакторинга и code review при сжатых сроках разработки. Технический долг приводит к замедлению добавления новых функций, росту дефектности и сложности передачи кода другим разработчикам.

### 2.1.3 Impacts (Влияние)

- Замедление добавления новых функций из-за сложности поддержки кода.
- Рост количества дефектов в уже работающих модулях.
- Невозможность передать код другому разработчику без длительного погружения.

### 2.1.4 Indicators (Признаки проявления)

- Время на реализацию типовой задачи увеличивается >20% от итерации к итерации.
- Количество багов при добавлении новых функций >3 в спринте.
- Покрытие кода unit-тестами <30%.

### 2.1.5 Mitigation Strategy (Стратегия смягчения)

1. Code review обязателен для всех изменений — оба разработчика проверяют код друг друга.
2. Выделение времени на рефакторинг в каждой итерации (до 20% спринта).
3. Использование статического анализа кода (SonarQube, Checkstyle) в CI/CD.

### 2.1.6 Contingency Plan (Стратегия наступления)

1. Приоритизация: рефакторинг критических модулей (аудит-лог, данные клиентов) в первую очередь.
2. Снижение планки качества для некритичных функций ради соблюдения сроков.

## 2.2 R2: Утечка конфиденциальных данных клиентов

### 2.2.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Средняя. Серьёзность: Критическая. Тип риска: Безопасность. Порог: обнаружение несанкционированного доступа.

### 2.2.2 Description (Описание)

Несанкционированный доступ к данным клиентов (личная информация, история операций, медицинские записи) через уязвимости в системе, перехват трафика или инсайдерские действия. Для клиник уровня Meth компрометация данных означает потерю репутации и судебные иски.

### 2.2.3 Impacts (Влияние)

- Юридические иски от клиентов, компенсации до 50 млн кредитов.
- Отзыв лицензии клиники регулятором (Протекторат Бей-Сити).
- Потеря доверия и закрытие бизнеса.

### 2.2.4 Indicators (Признаки проявления)

- Более 5 неудачных попыток входа с одного IP в течение 10 минут.
- Запросы к данным с IP-адресов за пределами сети клиники >1 в день.
- Срабатывание IDS/IPS >1 раза в неделю.

### 2.2.5 Mitigation Strategy (Стратегия смягчения)

1. Шифрование всех чувствительных данных (TLS для передачи, AES для хранения).
2. Аутентификация 2FA для всех учётных записей.
3. RBAC: строгое разграничение доступа по ролям сотрудников.
4. Аудит-лог с однократной записью (append-only), доступный только администратору.

### 2.2.6 Contingency Plan (Стратегия наступления)

1. Немедленная блокировка скомпрометированной учётной записи.
2. Запуск расследования: анализ audit-log, идентификация источника утечки.
3. Уведомление затронутых клиентов и регулятора.
4. Смена всех ключей шифрования и паролей.

## 2.3 R3: Срыв сроков разработки

### 2.3.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Высокая. Серьёзность: Средняя. Тип риска: Разработка (процессный). Порог: отставание от графика > 2 недель.

### 2.3.2 Description (Описание)

Невыполнение плана разработки в установленные сроки (4 месяца) из-за недооценки сложности, изменения требований, технических проблем или низкой производительности. Учитывая малый размер команды, любая задержка критична.

### 2.3.3 Impacts (Влияние)

- Невозможность завершить все запланированные функции к дедлайну.
- Сжатие фазы тестирования (риск пропуска критических дефектов).
- Недовольство заказчика, потеря репутации команды.

### 2.3.4 Indicators (Признаки проявления)

- Отставание от графика >10% в итерации (>2 дня из 20 рабочих).
- Более 30% задач переходят в следующий спринт.
- Переоценка трудозатрат >50% на >2 задачи подряд.

### 2.3.5 Mitigation Strategy (Стратегия смягчения)

1. Приоритизация требований: критичные функции реализуются в первую очередь.
2. Еженедельный review прогресса с заказчиком.
3. Буфер времени: 2 недели на непредвиденные задержки.

### 2.3.6 Contingency Plan (Стратегия наступления)

1. Пересмотр плана: перемещение некритичных функций в следующий релиз.
2. Фокус на рабочем MVP с базовым функционалом вместо полного набора функций.

## 2.4 R4: Недостаточное тестирование и регрессионные ошибки

### 2.4.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Высокая. Серьёзность: Высокая. Тип риска: Разработка (процессный). Порог: покрытие тестами < 20%.

В команде нет выделенного QA-инженера — тестирование выполняют те же 2 разработчика. При сжатии сроков тестирование страдает в первую очередь: unit-тесты не пишутся, регрессионное тестирование пропускается, критические дефекты уходят в продакшен.

### 2.4.2 Description (Описание)

Отсутствие выделенного QA-инженера и сжатые сроки приводят к пропуску этапов тестирования. Unit-тесты не покрывают критические модули, регрессионное тестирование не проводится, дефекты обнаруживаются уже в продакшене.

### 2.4.3 Impacts (Влияние)

- Критические дефекты в модулях аудит-лога и данных клиентов (юридические риски).
- Потеря данных или некорректная генерация сертификатов.
- Нестабильная работа системы в демонстрациях заказчику.

### 2.4.4 Indicators (Признаки проявления)

- Покрытие кода тестами <30% (для критических модулей <50%).
- Этап тестирования пропущен >1 раза в итерации.
- Повторное возникновение ранее исправленных багов >2 раза в месяц.

### 2.4.5 Mitigation Strategy (Стратегия смягчения)

1. Автоматизированное тестирование: unit + smoke-тесты в CI/CD на каждый коммит.
2. Определение критического функционала (core-модули), обязательного к тестированию.
3. Чек-лист регрессионного тестирования перед каждым релизом.

### 2.4.6 Contingency Plan (Стратегия наступления)

1. Приоритетное исправление критических дефектов перед добавлением новых функций.
2. Временное привлечение внешнего тестировщика (студент-стажёр).

## 2.5 R5: Технические проблемы интеграции и развёртывания

### 2.5.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Средняя. Серьёзность: Средняя. Тип риска: Разработка (технологический). Порог: 3+ неудачных сборки подряд.

### 2.5.2 Description (Описание)

Сложности при интеграции backend (Spring Boot), frontend (React) и базы данных (PostgreSQL), а также при развёртывании на сервере helios.cs.ifmo.ru (FreeBSD). Отличия окружения разработки от продакшена могут вызвать неожиданные ошибки.

### 2.5.3 Impacts (Влияние)

- Задержка развёртывания, невозможность показать работающий продукт к демо.
- Потеря времени на отладку инфраструктурных проблем.
- Нестабильная работа системы на целевом сервере.

### 2.5.4 Indicators (Признаки проявления)

- >3 неудачных сборки подряд в CI/CD.
- Ошибки Docker-сборки >2 раза в неделю.
- Проблемы с портами/правами на helios >1 раза в неделю.

### 2.5.5 Mitigation Strategy (Стратегия смягчения)

1. Контейнеризация через Docker Compose — единое окружение для разработки и сервера.
2. CI/CD: автоматическая сборка и тестирование при каждом push.
3. Раннее развёртывание прототипа на сервере (фаза Elaboration) для выявления проблем.

### 2.5.6 Contingency Plan (Стратегия наступления)

1. Откат к предыдущей стабильной версии при критических ошибках.
2. Привлечение DevOps-специалиста (внешний консультант) для настройки сервера.
3. Временное использование альтернативного окружения (например, облачный сервер).

## 2.6 R6: Проблемы производительности и масштабирования

### 2.6.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Средняя. Серьёзность: Средняя. Тип риска: Разработка (технологический). Порог: время отклика API > 1 сек при 10+ запросах.

### 2.6.2 Description (Описание)

Система SCMS должна поддерживать до 50 одновременных пользователей с откликом ≤0.5 сек для персонала и ≤100 мс для мониторинга needlecast. Некорректная архитектура БД, отсутствие кэширования или неоптимальные запросы могут привести к падению производительности в пиковые моменты.

### 2.6.3 Impacts (Влияние)

- Задержки отображения данных мониторинга needlecast (превышение 100 мс).
- Невозможность одновременной работы нескольких сотрудников с каталогом sleeves.
- Снижение удовлетворённости заказчика при демонстрации системы.

### 2.6.4 Indicators (Признаки проявления)

- Время отклика API >500 мс при 10+ одновременных запросах.
- Загрузка страниц каталога >3 сек.
- Рост потребления памяти/CPU >20% без увеличения нагрузки.

### 2.6.5 Mitigation Strategy (Стратегия смягчения)

1. Кэширование часто запрашиваемых данных (каталог sleeves) через Redis.
2. Оптимизация запросов к БД (индексы, пагинация, N+1 query detection).
3. Нагрузочное тестирование в CI/CD после каждого крупного изменения.

### 2.6.6 Contingency Plan (Стратегия наступления)

1. Вертикальное масштабирование сервера (увеличение ресурсов helios).
2. Добавление реплик чтения БД для разгрузки основной базы.
3. Временное отключение некритичных функций (аналитика, отчёты) под нагрузкой.

## 2.7 R7: Политические санкции и изменение регулирования

### 2.7.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Средняя. Серьёзность: Критическая. Тип риска: Политический. Порог: официальное уведомление от Протектората.

### 2.7.2 Description (Описание)

Протекторат ООН или сенаторы Бей-Сити могут ввести новые ограничения на манипуляции с DHF (Digital Human Freight), включая требования обязательного аудита, лицензирования каждого needlecast или полный запрет на определённые виды переноса. Клиника работает в серой зоне закона — любое ужесточение регулирования может потребовать кардинального изменения функционала SCMS или приостановки операций.

### 2.7.3 Impacts (Влияние)

- Необходимость срочной доработки системы под новые требования регуляторов.
- Приостановка операций клиники на время приведения системы в соответствие.
- Потеря лицензии клиники, невозможность проведения needlecast.
- Штрафные санкции от Протектората до 10 млн кредитов.

### 2.7.4 Indicators (Признаки проявления)

- Публичные заявления сенаторов >2 раза в месяц о регулировании DHF.
- Внеплановые проверки Протекторатом >1 раза в квартал.
- Утечки в СМИ о несчастных случаях >1 раза в месяц.

### 2.7.5 Mitigation Strategy (Стратегия смягчения)

1. Модульная архитектура SCMS, позволяющая быстро добавлять новые поля отчётности и проверки.
2. Встроенный аудит-лог по всем операциям для предоставления регуляторам.
3. Разработка системы генерации отчётов для Протектората (гибкие шаблоны).

### 2.7.6 Contingency Plan (Стратегия наступления)

1. Юридический аудит системы внешними консультантами по требованию Протектората.
2. Быстрая имплементация новых требований через выделенную итерацию разработки.
3. Привлечение Envoy Corps как консультантов для подтверждения безопасности процедур.

## 2.8 R8: Давление религиозных и общественных организаций

### 2.8.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Высокая. Серьёзность: Средняя. Тип риска: Политический. Порог: появление пикетов или публикации в топ-СМИ.

### 2.8.2 Description (Описание)

Католическая церковь осуждает использование кортикальных стеков и перенос сознания как вмешательство в божественную природу человека. Церковь регулярно организует пикеты у клиники, публикует статьи в СМИ Бей-Сити и лоббирует сенаторов для введения запретов. Негативное освещение в прессе может отпугнуть клиентов Meths, требующих абсолютной приватности.

### 2.8.3 Impacts (Влияние)

- Отток клиентов Meths, не желающих ассоциироваться со скандальной клиникой.
- Давление на владельца здания со стороны арендодателей (угроза расторжения договора аренды).
- Дополнительные требования к системе по сокрытию информации о клиентах.
- Усиление охраны и проверок безопасности (рост операционных расходов).

### 2.8.4 Indicators (Признаки проявления)

- Пикеты у здания клиники >1 раза в месяц.
- Критические статьи в СМИ >2 раза в месяц.
- Запросы от журналистов >3 раз в месяц.

### 2.8.5 Mitigation Strategy (Стратегия смягчения)

1. Усиленная система безопасности и анонимизации данных клиентов в SCMS.
2. Модуль управления репутацией: мониторинг упоминаний в СМИ, генерация ответов.
3. Строгое разграничение доступа: даже администратор не видит полные данные Meth без дополнительной авторизации.

### 2.8.6 Contingency Plan (Стратегия наступления)

1. Найм PR-агентства для управления репутацией (внешний бюджет).
2. Временное приостановление приёма новых клиентов до снижения медийного давления.
3. Перенаправление трафика через анонимные прокси и VPN для сокрытия IP клиники.

## 2.9 R9: Юридические претензии от клиентов и семей Meth

### 2.9.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Средняя. Серьёзность: Высокая. Тип риска: Юридический. Порог: получение официальной претензии от адвоката Meth.

### 2.9.2 Description (Описание)

Meths и их семьи могут подать судебные иски против клиники в случаях: несовместимость тела со стеком (stack shock), фрагментация личности после переноса, изменение деловых качеств Meth (что влияет на завещания и контракты), утечка данных о состоянии здоровья. Каждый иск может стоить клинике до 50 млн кредитов компенсации.

### 2.9.3 Impacts (Влияние)

- Финансовые потери на компенсации и судебные издержки.
- Требования к SCMS по предоставлению полных audit-log по каждому кейсу.
- Усложнение процесса сертификации (дополнительные проверки Psychosurgeon).
- Заморозка счетов клиники по решению суда, блокировка операций.

### 2.9.4 Indicators (Признаки проявления)

- Жалобы Meths/представителей >1 раза в квартал.
- Запросы от адвокатов >1 раза в квартал.
- Претензии к сертификатам >1 раза в полгода.

### 2.9.5 Mitigation Strategy (Стратегия смягчения)

1. Детальный аудит-лог каждой операции с цифровой подписью сотрудника.
2. Электронные сертификаты совместимости с криптографической подписью Psychosurgeon.
3. Хранение всех медицинских записей в неизменяемом виде (append-only storage).
4. Встроенные чеклисты и протоколы для Psychosurgeon (минимизация человеческой ошибки).

### 2.9.6 Contingency Plan (Стратегия наступления)

1. Автоматическая генерация полного отчёта по кейсу для юридического отдела.
2. Блокировка доступа к данным кейса для всех, кроме юридической команды.
3. Внешний аудит системы независимым экспертом для подтверждения корректности.

## 2.10 R10: Зависимость от внешних поставщиков

### 2.10.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Средняя. Серьёзность: Высокая. Тип риска: Операционный. Порог: отказ API поставщика > 4 часов.

### 2.10.2 Description (Описание)

SCMS зависит от внешних поставщиков: генетические архивы (данные о клонированных телах), охранные корпорации (системы безопасности и квантовое шифрование для хранилищ DHF), облачные сервисы (мониторинг). Срыв поставок, повышение цен (до 300% для клиник уровня Meth), банкротство поставщика могут парализовать работу клиники.

### 2.10.3 Impacts (Влияние)

- Невозможность получения данных о доступных sleeves (остановка подбора тела).
- Потеря защищённого канала для передачи DHF (невозможность needlecast).
- Рост операционных расходов при переходе на альтернативных поставщиков.
- Необходимость экстренной интеграции с новыми API поставщиков в SCMS.

### 2.10.4 Indicators (Признаки проявления)

- Уведомления об изменении условий контрактов >1 раза в квартал.
- Сбои API генетических архивов >2 раза в месяц.
- Отказы систем безопасности >1 раза в месяц.

### 2.10.5 Mitigation Strategy (Стратегия смягчения)

1. Поддержка интеграции с минимум двумя поставщиками каждого типа (архивы, охрана).
2. Абстрактный слой интеграции в архитектуре SCMS (легкая смена провайдера).
3. Регулярное резервное копирование данных генетических архивов локально.
4. Локальное кэширование критичных данных (каталог sleeves) для автономной работы.

### 2.10.6 Contingency Plan (Стратегия наступления)

1. Экстренный переход на резервного поставщика (переключение API-ключа в SCMS).
2. Использование локального хранилища данных до восстановления основного поставщика.
3. Ручной ввод данных при недоступности API (режим офлайн с последующей синхронизацией).
