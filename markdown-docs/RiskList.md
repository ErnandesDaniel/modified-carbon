# 2. Risks (Риски)

## R1: Технический долг и снижение качества кода
**Вероятность:** Высокая. **Серьёзность:** Средняя. **Тип риска:** Разработка.

**Описание:** В условиях жёсткого дедлайна (4 месяца) и малой команды (2 разработчика) возникает соблазн сокращать рефакторинг, пропускать code review и писать «быстрые» решения. Технический долг накапливается, что замедляет разработку в поздних итерациях и увеличивает количество дефектов.

**Влияние:**
- Замедление добавления новых функций из-за сложности поддержки кода.
- Рост количества дефектов в уже работающих модулях.
- Невозможность передать код другому разработчику без длительного погружения.

**Индикаторы (Уровни опасности):**
- 🟢 **Уровень 1:** Время реализации типовой задачи растёт <10%. Покрытие тестами ≥40%. Code review проходит в 100% PR.
- 🟡 **Уровень 2:** Рост времени 10–20%. Покрытие 30–40%. Code review пропускается в 1 из 5 PR.
- 🟠 **Уровень 3:** Рост времени 20–35%. Покрытие <30%. >3 багов на фичу в спринте.
- 🔴 **Уровень 4:** Рост времени >35%. Покрытие <20%. Критические модули (аудит, данные клиентов) нестабильны.

**Mitigation:** Обязательный code review, 20% времени спринта на рефакторинг, SonarQube/Checkstyle в CI/CD.

**Contingency:** Приоритетный рефакторинг ядра (аудит, данные клиентов), временное снижение требований к некритичному UI.

## R2: Утечка конфиденциальных данных клиентов
**Вероятность:** Средняя. **Серьёзность:** Критическая. **Тип риска:** Безопасность.

**Описание:** Несанкционированный доступ к данным клиентов (личная информация, история операций, медицинские записи) через уязвимости в системе, перехват трафика или инсайдерские действия. Для клиник уровня Meth компрометация данных означает потерю репутации и судебные иски.

**Влияние:**
- Юридические иски от клиентов, компенсации до 50 млн кредитов.
- Отзыв лицензии клиники регулятором (Протекторат Бей-Сити).
- Потеря доверия и закрытие бизнеса.

**Индикаторы:**
- 🟢 **Ур. 1:** 0 инцидентов. Все логи в норме. 2FA активен у 100% staff.
- 🟡 **Ур. 2:** 1–2 подозрительных входа/неделю. Успешно заблокированы.
- 🟠 **Ур. 3:** 3–5 неудачных попыток с одного IP/день. Запросы извне сети клиники.
- 🔴 **Ур. 4:** Подтверждённая утечка или обход RBAC. Доступ к audit-log извне.

**Mitigation:** Шифрование всех чувствительных данных (TLS для передачи, AES для хранения). Аутентификация 2FA для всех учётных записей. RBAC: строгое разграничение доступа по ролям сотрудников. Аудит-лог с однократной записью (append-only), доступный только администратору.

**Contingency:** Немедленная блокировка скомпрометированной учётной записи. Запуск расследования: анализ audit-log, идентификация источника утечки. Уведомление затронутых клиентов и регулятора. Смена всех ключей шифрования и паролей.

## R3: Срыв сроков разработки
**Вероятность:** Высокая. **Серьёзность:** Средняя. **Тип риска:** Разработка (процессный).

**Описание:** Невыполнение плана разработки в установленные сроки (4 месяца) из-за недооценки сложности, изменения требований, технических проблем или низкой производительности. Учитывая малый размер команды, любая задержка критична.

**Влияние:**
- Невозможность завершить все запланированные функции к дедлайну.
- Сжатие фазы тестирования (риск пропуска критических дефектов).
- Недовольство заказчика, потеря репутации команды.

**Индикаторы:**
- 🟢 **Ур. 1:** Отставание ≤5% от плана спринта.
- 🟡 **Ур. 2:** Отставание 5–15%. >20% задач переносятся.
- 🟠 **Ур. 3:** Отставание 15–25%. Критические задачи блокируются >3 дней.
- 🔴 **Ур. 4:** Отставание >25%. Невозможность закрыть итерацию без сокращения scope.

**Mitigation:** Приоритизация требований: критичные функции реализуются в первую очередь. Еженедельный review прогресса с заказчиком. Буфер времени: 2 недели на непредвиденные задержки.

**Contingency:** Пересмотр плана: перемещение некритичных функций в следующий релиз. Фокус на рабочем MVP с базовым функционалом вместо полного набора функций.

---

## R4: Недостаточное тестирование и регрессионные ошибки
**Вероятность:** Высокая. **Серьёзность:** Высокая. **Тип риска:** Разработка (процессный).

**Описание:** В команде нет выделенного QA-инженера — тестирование выполняют те же 2 разработчика. При сжатии сроков тестирование страдает в первую очередь: unit-тесты не пишутся, регрессионное тестирование пропускается, критические дефекты уходят в продакшен.

**Влияние:**
- Критические дефекты в модулях аудит-лога и данных клиентов (юридические риски).
- Потеря данных или некорректная генерация сертификатов.
- Нестабильная работа системы в демонстрациях заказчику.

**Индикаторы:**
- 🟢 **Ур. 1:** Покрытие ≥70%. 0 пропущенных регрессионных сценариев.
- 🟡 **Ур. 2:** Покрытие 50–70%. 1–2 пропущенных сценария за итерацию.
- 🟠 **Ур. 3:** Покрытие 30–50%. >3 регрессионных бага/мес. Тесты запускаются вручную.
- 🔴 **Ур. 4:** Покрытие <30%. CI/CD пайплайн падает >50% времени. Критические баги уходят на демо.

**Mitigation:** Автоматизированное тестирование: unit + smoke-тесты в CI/CD на каждый коммит. Определение критического функционала (core-модули), обязательного к тестированию. Чек-лист регрессионного тестирования перед каждым релизом.

**Contingency:** Приоритетное исправление критических дефектов перед добавлением новых функций. Временное привлечение внешнего тестировщика (студент-стажёр).

## R5: Технические проблемы интеграции и развёртывания
**Вероятность:** Средняя. **Серьёзность:** Средняя. **Тип риска:** Разработка (технологический).

**Описание:** Сложности при интеграции backend (Spring Boot), frontend (React) и базы данных (PostgreSQL), а также при развёртывании на сервере helios.cs.ifmo.ru (FreeBSD). Отличия окружения разработки от продакшена могут вызвать неожиданные ошибки.

**Влияние:**
- Задержка развёртывания, невозможность показать работающий продукт к демо.
- Потеря времени на отладку инфраструктурных проблем.
- Нестабильная работа системы на целевом сервере.

**Индикаторы:**
- 🟢 **Ур. 1:** 0–1 failed build в CI/CD за неделю.
- 🟡 **Ур. 2:** 2–3 failed build. Локальные порт-конфликты решаются за <1 часа.
- 🟠 **Ур. 3:** 4–6 failed build. Ошибки миграций БД или CORS >2 раз в неделю.
- 🔴 **Ур. 4:** >6 failed build. Невозможность запустить full-stack локально или на helios.

**Mitigation:** Контейнеризация через Docker Compose — единое окружение для разработки и сервера. CI/CD: автоматическая сборка и тестирование при каждом push. Раннее развёртывание прототипа на сервере (фаза Elaboration) для выявления проблем.

**Contingency:** Откат к предыдущей стабильной версии при критических ошибках. Привлечение DevOps-специалиста (внешний консультант) для настройки сервера. Временное использование альтернативного окружения (например, облачный сервер).

## R6: Проблемы производительности и масштабирования
**Вероятность:** Средняя. **Серьёзность:** Средняя. **Тип риска:** Разработка (технологический).

**Описание:** Система SCMS должна поддерживать до 50 одновременных пользователей с откликом ≤0.5 сек для персонала и ≤100 мс для мониторинга needlecast. Некорректная архитектура БД, отсутствие кэширования или неоптимальные запросы могут привести к падению производительности в пиковые моменты.

**Влияние:**
- Задержки отображения данных мониторинга needlecast (превышение 100 мс).
- Невозможность одновременной работы нескольких сотрудников с каталогом sleeves.
- Снижение удовлетворённости заказчика при демонстрации системы.

**Индикаторы:**
- 🟢 **Ур. 1:** p95 отклика ≤300 мс при 20 пользователях.
- 🟡 **Ур. 2:** p95 300–500 мс при 30 пользователях. CPU/RAM ≤70%.
- 🟠 **Ур. 3:** p95 >500 мс при 40 пользователях. N+1 queries в логах, кэш-промахи >15%.
- 🔴 **Ур. 4:** p95 >1000 мс, таймауты БД, утечки памяти >20% за час.

**Mitigation:** Кэширование часто запрашиваемых данных (каталог sleeves) через Redis. Оптимизация запросов к БД (индексы, пагинация, N+1 query detection). Нагрузочное тестирование в CI/CD после каждого крупного изменения.

**Contingency:** Вертикальное масштабирование сервера (увеличение ресурсов helios). Добавление реплик чтения БД для разгрузки основной базы. Временное отключение некритичных функций (аналитика, отчёты) под нагрузкой.

## R7: Политические санкции и изменение регулирования
**Вероятность:** Средняя. **Серьёзность:** Критическая. **Тип риска:** Политический.

**Описание:** Протекторат ООН или сенаторы Бей-Сити могут ввести новые ограничения на манипуляции с DHF (Digital Human Freight), включая требования обязательного аудита, лицензирования каждого needlecast или полный запрет на определённые виды переноса. Клиника работает в серой зоне закона — любое ужесточение регулирования может потребовать кардинального изменения функционала SCMS или приостановки операций.

**Влияние:**
- Необходимость срочной доработки системы под новые требования регуляторов.
- Приостановка операций клиники на время приведения системы в соответствие.
- Потеря лицензии клиники, невозможность проведения needlecast.
- Штрафные санкции от Протектората до 10 млн кредитов.

**Индикаторы:**
- 🟢 **Ур. 1:** 0 официальных уведомлений. Спокойный медиа-фон.
- 🟡 **Ур. 2:** Публичные обсуждения регулирований. 1 проверка/квартал.
- 🟠 **Ур. 3:** Официальные запросы от Протектората. 2+ проверки/квартал.
- 🔴 **Ур. 4:** Введение новых ограничений. Требование срочного аудита или заморозка лицензий.

**Mitigation:** Модульная архитектура SCMS, позволяющая быстро добавлять новые поля отчётности и проверки. Встроенный аудит-лог по всем операциям для предоставления регуляторам. Разработка системы генерации отчётов для Протектората (гибкие шаблоны).

**Contingency:** Юридический аудит системы внешними консультантами по требованию Протектората. Быстрая имплементация новых требований через выделенную итерацию разработки. Привлечение Envoy Corps как консультантов для подтверждения безопасности процедур.

## R8: Давление религиозных и общественных организаций
**Вероятность:** Высокая. **Серьёзность:** Средняя. **Тип риска:** Политический.

**Описание:** Католическая церковь осуждает использование кортикальных стеков и перенос сознания как вмешательство в божественную природу человека. Церковь регулярно организует пикеты у клиники, публикует статьи в СМИ Бей-Сити и лоббирует сенаторов для введения запретов. Негативное освещение в прессе может отпугнуть клиентов Meths, требующих абсолютной приватности.

**Влияние:**
- Отток клиентов Meths, не желающих ассоциироваться со скандальной клиникой.
- Давление на владельца здания со стороны арендодателей (угроза расторжения договора аренды).
- Дополнительные требования к системе по сокрытию информации о клиентах.
- Усиление охраны и проверок безопасности (рост операционных расходов).

**Индикаторы:**
- 🟢 **Ур. 1:** 0 пикетов/статей. Нейтральный фон.
- 🟡 **Ур. 2:** 1 пикет/мес или 1–2 статьи. Локальный резонанс.
- 🟠 **Ур. 3:** 2–3 пикета/мес, запросы от СМИ >3/мес. Угрозы арендодателю.
- 🔴 **Ур. 4:** Массовые протесты, блокировка входа в клинику, требование закрытия от сената.

**Mitigation:** Усиленная система безопасности и анонимизации данных клиентов в SCMS. Модуль управления репутацией: мониторинг упоминаний в СМИ, генерация ответов. Строгое разграничение доступа: даже администратор не видит полные данные Meth без дополнительной авторизации.

**Contingency:** Найм PR-агентства для управления репутацией (внешний бюджет). Временное приостановление приёма новых клиентов до снижения медийного давления. Перенаправление трафика через анонимные прокси и VPN для сокрытия IP клиники.

## R9: Юридические претензии от клиентов и семей Meth
**Вероятность:** Средняя. **Серьёзность:** Высокая. **Тип риска:** Юридический.

**Описание:** Meths и их семьи могут подать судебные иски против клиники в случаях: несовместимость тела со стеком (stack shock), фрагментация личности после переноса, изменение деловых качеств Meth (что влияет на завещания и контракты), утечка данных о состоянии здоровья. Каждый иск может стоить клинике до 50 млн кредитов компенсации.

**Влияние:**
- Финансовые потери на компенсации и судебные издержки.
- Требования к SCMS по предоставлению полных audit-log по каждому кейсу.
- Усложнение процесса сертификации (дополнительные проверки Psychosurgeon).
- Заморозка счетов клиники по решению суда, блокировка операций.

**Индикаторы:**
- 🟢 **Ур. 1:** 0 претензий. Все сертификаты подписаны криптографически.
- 🟡 **Ур. 2:** 1 жалоба/квартал. Решается internally.
- 🟠 **Ур. 3:** Запросы от адвокатов, оспаривание сертификатов >1 раза/полгода.
- 🔴 **Ур. 4:** Официальный иск, заморозка операций, требование внешнего аудита системы.

**Mitigation:** Детальный аудит-лог каждой операции с цифровой подписью сотрудника. Электронные сертификаты совместимости с криптографической подписью Psychosurgeon. Хранение всех медицинских записей в неизменяемом виде (append-only storage). Встроенные чеклисты и протоколы для Psychosurgeon (минимизация человеческой ошибки).

**Contingency:** Автоматическая генерация полного отчёта по кейсу для юридического отдела. Блокировка доступа к данным кейса для всех, кроме юридической команды. Внешний аудит системы независимым экспертом для подтверждения корректности.

## R10: Зависимость от внешних поставщиков
**Вероятность:** Средняя. **Серьёзность:** Высокая. **Тип риска:** Операционный.

**Описание:** SCMS зависит от внешних поставщиков: генетические архивы (данные о клонированных телах), охранные корпорации (системы безопасности и квантовое шифрование для хранилищ DHF), облачные сервисы (мониторинг). Срыв поставок, повышение цен (до 300% для клиник уровня Meth), банкротство поставщика могут парализовать работу клиники.

**Влияние:**
- Невозможность получения данных о доступных sleeves (остановка подбора тела).
- Потеря защищённого канала для передачи DHF (невозможность needlecast).
- Рост операционных расходов при переходе на альтернативных поставщиков.
- Необходимость экстренной интеграции с новыми API поставщиков в SCMS.

**Индикаторы:**
- 🟢 **Ур. 1:** Uptime API поставщиков ≥99.9%. 0 сбоев/мес.
- 🟡 **Ур. 2:** 1–2 коротких сбоя (<1 часа). Авто-failover срабатывает.
- 🟠 **Ур. 3:** Сбои >4 часов. Рост цен >15%. Ручной ввод данных >2 раз/нед.
- 🔴 **Ур. 4:** Банкротство поставщика или отказ API >24 часов. Нет резервного канала.

**Mitigation:** Поддержка интеграции с минимум двумя поставщиками каждого типа (архивы, охрана). Абстрактный слой интеграции в архитектуре SCMS (легкая смена провайдера). Регулярное резервное копирование данных генетических архивов локально. Локальное кэширование критичных данных (каталог sleeves) для автономной работы.

**Contingency:** Экстренный переход на резервного поставщика (переключение API-ключа в SCMS). Использование локального хранилища данных до восстановления основного поставщика. Ручной ввод данных при недоступности API (режим офлайн с последующей синхронизацией).

## R11: Нестабильность требований и изменение scope
**Вероятность:** Средняя. **Серьёзность:** Высокая. **Тип риска:** Процессы.

**Описание:** Заказчик или стейкхолдеры вносят изменения в FR после базовой линии SRS.

**Влияние:**
- Переделка архитектуры, конфликты бизнес-логики, сдвиг сроков.

**Индикаторы:**
- 🟢 **Ур. 1:** 0–1 изменение требований за итерацию. Все через CR.
- 🟡 **Ур. 2:** 2 изменения. Небольшие правки UI/отчётов.
- 🟠 **Ур. 3:** 3–4 изменения. Затрагивают бизнес-логику (FR-007, FR-010).
- 🔴 **Ур. 4:** >5 изменений. Пересмотр ядра системы, остановка разработки на аудит.

**Mitigation:** Заморозка SRS после Elaboration, формализованный Change Control Board, модульная архитектура.

**Contingency:** Выделение отдельной итерации под доработки, пересмотр приоритетов, фиксация влияния на бюджет/сроки в CR.

## R12: Критические задержки в модуле мониторинга needlecast
**Вероятность:** Средняя. **Серьёзность:** Критическая. **Тип риска:** Разработка.

**Описание:** FR-007 и SRS 3.4.1 требуют фиксации этапов needlecast в реальном времени. Ошибки в WebSocket/API или блокировки БД могут привести к потере данных переноса.

**Влияние:**
- Невозможность оперативно реагировать на отклонения, риск stack shock, юридическая ответственность клиники.

**Индикаторы:**
- 🟢 **Ур. 1:** Задержка обновления статуса ≤80 мс. 0 потерянных сообщений WebSocket.
- 🟡 **Ур. 2:** Задержка 80–120 мс. Редкие переподключения клиентов (<2/час).
- 🟠 **Ур. 3:** Задержка >150 мс. Потеря >5% событий мониторинга. Блокировки транзакций >3/мин.
- 🔴 **Ур. 4:** Задержка >500 мс, разрыв соединения >10 мин, данные этапов не сохраняются в БД.

**Mitigation:** Выделенный микросервис/эндпоинт для мониторинга, асинхронная запись в БД, heartbeat-механизм, резервное логирование на диск.

**Contingency:** Переключение на офлайн-протокол (ручная фиксация + последующая синхронизация), экстренный рестарт сервиса мониторинга, уведомление Psychosurgeon.

## R13: Низкое покрытие тестами критических бизнес-процессов
**Вероятность:** Высокая. **Серьёзность:** Высокая. **Тип риска:** Процессы.

**Описание:** TestPlan требует end-to-end проверки циклов: подбор → needlecast → валидация → сертификация. Пропуск этих сценариев ведёт к скрытым дефектам.

**Влияние:**
- Ошибки в генерации сертификатов (FR-010), потеря статуса sleeve, невозможность выпуска клиента.

**Индикаторы:**
- 🟢 **Ур. 1:** 100% core-циклов покрыты e2e-тестами. 0 падений в CI.
- 🟡 **Ур. 2:** 80–99% покрыто. 1–2 flaky-теста.
- 🟠 **Ур. 3:** 50–79% покрыто. Сценарии валидации/сертификации тестируются вручную.
- 🔴 **Ур. 4:** <50% покрыто. Критические пути (needlecast→cert) не автоматизированы, высокий риск регрессии.

**Mitigation:** Приоритет автоматизации core-циклов, mock-данные для стабильности, gate в CI: merge только при pass e2e.

**Contingency:** Ручное прогоняние 4 основных сценариев перед каждым релизом, отложенный merge фич, не затрагивающих core.

## R14: Рассинхрон тестового и продакшен-окружения
**Вероятность:** Средняя. **Серьёзность:** Средняя. **Тип риска:** Инфраструктура.

**Описание:** Различия в версиях ОС, БД, переменных окружения между локальной машиной, CI и helios.cs.ifmo.ru.

**Влияние:**
- "Работает у меня, но не на сервере", задержки деплоя, скрытые баги в проде.

**Индикаторы:**
- 🟢 **Ур. 1:** 100% parity окружений. Docker-образы идентичны.
- 🟡 **Ур. 2:** 1–2 незначительных различия (пути, логи). Решаются за <2 часов.
- 🟠 **Ур. 3:** Различия в версиях БД/Java. Миграции падают на helios.
- 🔴 **Ур. 4:** Критический рассинхрон. Приложение не стартует на проде, данные теряются при деплое.

**Mitigation:** Infrastructure as Code (Docker Compose + env-файлы), automated deployment scripts, staging-сервер, чек-лист деплоя.

**Contingency:** Откат к предыдущему образу, ручная настройка окружения по документации, заморозка релиза до устранения рассинхрона.

# 3. Risk Review & Update Procedure

- Ревизия Risk List проводится **каждые 2 недели** на планировании спринта.
- При достижении **🟠 или 🔴 уровня индикатора** PM инициирует план коррекции в течение 48 часов.
- Все изменения вносятся в Change List документа с указанием даты и утверждения.
