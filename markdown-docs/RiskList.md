# 2. Risks (Риски)

## 2.1 R1: Технический долг и снижение качества кода

### 2.1.1 Risk Magnitude or Ranking (Вероятность появления и серьезность)

Вероятность: Высокая. Серьёзность: Средняя. Тип риска: Процессный. Порог: покрытие тестами < 30%.

В условиях жёсткого дедлайна и малой команды (2 разработчика) возникает соблазн сокращать рефакторинг, пропускать code review и писать «быстрые» решения. Технический долг накапливается, что замедляет разработку в поздних итерациях и увеличивает количество дефектов.

### 2.1.2 Description (Описание)

Накопление неоптимального кода, пропуск рефакторинга и code review при сжатых сроках разработки. Технический долг приводит к замедлению добавления новых функций, росту дефектности и сложности передачи кода другим разработчикам.

### 2.1.3 Impacts (Влияние)

- Замедление добавления новых функций из-за сложности поддержки кода.
- Рост количества дефектов в уже работающих модулях.
- Невозможность передать код другому разработчику без длительного погружения.

### 2.1.4 Indicators (Признаки проявления)

| Параметр | Пороговое значение | Источник данных |
|----------|--------------------|-----------------|
| Время на реализацию типовой задачи | Увеличение >20% от итерации к итерации | GitLab Issue Board, time tracking |
| Количество багов при добавлении новых функций | >3 в спринте | GitLab Issues |
| Покрытие кода unit-тестами | <30% | JaCoCo отчёт в CI/CD |

### 2.1.5 Mitigation Strategy (Стратегия смягчения)

1. Code review обязателен для всех изменений — оба разработчика проверяют код друг друга.
2. Выделение времени на рефакторинг в каждой итерации (до 20% спринта).
3. Использование статического анализа кода (SonarQube, Checkstyle) в CI/CD.

### 2.1.6 Contingency Plan (Стратегия наступления)

1. Приоритизация: рефакторинг критических модулей (аудит-лог, данные клиентов) в первую очередь.
2. Снижение планки качества для некритичных функций ради соблюдения сроков.

## 2.2 R2: Технические проблемы интеграции и развёртывания

### 2.2.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Средняя. Серьёзность: Средняя. Тип риска: Технологический. Порог: 3+ неудачных сборки подряд.

### 2.2.2 Description (Описание)

Сложности при интеграции backend (Spring Boot), frontend (React) и базы данных (PostgreSQL), а также при развёртывании на сервере helios.cs.ifmo.ru (FreeBSD). Отличия окружения разработки от продакшена могут вызвать неожиданные ошибки.

### 2.2.3 Impacts (Влияние)

- Задержка развёртывания, невозможность показать работающий продукт к демо.
- Потеря времени на отладку инфраструктурных проблем.
- Нестабильная работа системы на целевом сервере.

### 2.2.4 Indicators (Признаки проявления)

| Параметр | Пороговое значение | Источник данных |
|----------|--------------------|-----------------|
| Неудачные сборки подряд в CI/CD | >3 подряд | GitLab CI/CD pipeline |
| Ошибки Docker-сборки | >2 раза в неделю | GitLab CI/CD pipeline |
| Проблемы с портами/правами на helios | >1 раза в неделю | Серверные логи, мониторинг |

### 2.2.5 Mitigation Strategy (Стратегия смягчения)

1. Контейнеризация через Docker Compose — единое окружение для разработки и сервера.
2. CI/CD: автоматическая сборка и тестирование при каждом push.
3. Раннее развёртывание прототипа на сервере (фаза Elaboration) для выявления проблем.

### 2.2.6 Contingency Plan (Стратегия наступления)

1. Откат к предыдущей стабильной версии при критических ошибках.
2. Привлечение DevOps-специалиста (внешний консультант) для настройки сервера.
3. Временное использование альтернативного окружения (например, облачный сервер).

## 2.3 R3: Срыв сроков разработки

### 2.3.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Высокая. Серьёзность: Средняя. Тип риска: Процессный. Порог: отставание от графика > 2 недель.

### 2.3.2 Description (Описание)

Невыполнение плана разработки в установленные сроки из-за недооценки сложности, изменения требований, технических проблем или низкой производительности. Учитывая малый размер команды, любая задержка критична.

### 2.3.3 Impacts (Влияние)

- Невозможность завершить все запланированные функции к дедлайну.
- Сжатие фазы тестирования (риск пропуска критических дефектов).
- Недовольство заказчика, потеря репутации команды.

### 2.3.4 Indicators (Признаки проявления)

| Параметр | Пороговое значение | Источник данных |
|----------|--------------------|-----------------|
| Отставание от графика в итерации | >10% (>2 дня из 20 рабочих) | GitLab Issue Board, burn-down chart |
| Задачи, переходящие в следующий спринт | >30% от запланированных | GitLab Issue Board |
| Переоценка трудозатрат подряд | >50% на >2 задачи | GitLab Issue Board, time tracking |

### 2.3.5 Mitigation Strategy (Стратегия смягчения)

1. Приоритизация требований: критичные функции реализуются в первую очередь.
2. Еженедельный review прогресса с заказчиком.
3. Буфер времени: 2 недели на непредвиденные задержки.

### 2.3.6 Contingency Plan (Стратегия наступления)

1. Пересмотр плана: перемещение некритичных функций в следующий релиз.
2. Фокус на рабочем MVP с базовым функционалом вместо полного набора функций.

## 2.4 R4: Недостаточное тестирование и регрессионные ошибки

### 2.4.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Высокая. Серьёзность: Высокая. Тип риска: Процессный. Порог: покрытие тестами < 20%.

В команде нет выделенного QA-инженера — тестирование выполняют те же 2 разработчика. При сжатии сроков тестирование страдает в первую очередь: unit-тесты не пишутся, регрессионное тестирование пропускается, критические дефекты уходят в продакшен.

### 2.4.2 Description (Описание)

Отсутствие выделенного QA-инженера и сжатые сроки приводят к пропуску этапов тестирования. Unit-тесты не покрывают критические модули, регрессионное тестирование не проводится, дефекты обнаруживаются уже в продакшене.

### 2.4.3 Impacts (Влияние)

- Критические дефекты в модулях аудит-лога и данных клиентов.
- Потеря данных или некорректная генерация сертификатов.
- Нестабильная работа системы в демонстрациях заказчику.

### 2.4.4 Indicators (Признаки проявления)

| Параметр | Пороговое значение | Источник данных |
|----------|--------------------|-----------------|
| Покрытие кода тестами (общее) | <30% | JaCoCo отчёт в CI/CD |
| Покрытие кода тестами (критические модули) | <50% | JaCoCo отчёт в CI/CD |
| Этап тестирования пропущен в итерации | >1 раза | Sprint review, TestPlan |
| Повторное возникновение ранее исправленных багов | >2 раз в месяц | GitLab Issues |

### 2.4.5 Mitigation Strategy (Стратегия смягчения)

1. Автоматизированное тестирование: unit + smoke-тесты в CI/CD на каждый коммит.
2. Определение критического функционала (core-модули), обязательного к тестированию.
3. Чек-лист регрессионного тестирования перед каждым релизом.

### 2.4.6 Contingency Plan (Стратегия наступления)

1. Приоритетное исправление критических дефектов перед добавлением новых функций.
2. Временное привлечение внешнего тестировщика (студент-стажёр).

## 2.5 R5: Проблемы производительности и масштабирования

### 2.5.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Средняя. Серьёзность: Средняя. Тип риска: Технологический. Порог: время отклика API > 1 сек при 10+ запросах.

Система SCMS должна поддерживать до 50 одновременных пользователей с откликом ≤0.5 сек для персонала и ≤100 мс для мониторинга needlecast. Некорректная архитектура БД, отсутствие кэширования или неоптимальные запросы могут привести к падению производительности в пиковые моменты.

### 2.5.2 Description (Описание)

Система не справляется с нагрузкой из-за неоптимальных SQL-запросов, отсутствия кэширования или неправильной настройки PostgreSQL. Мониторинг needlecast через WebSocket может превышать допустимую задержку в 100 мс.

### 2.5.3 Impacts (Влияние)

- Задержки отображения данных мониторинга needlecast (превышение 100 мс).
- Невозможность одновременной работы нескольких сотрудников с каталогом sleeves.
- Снижение удовлетворённости заказчика при демонстрации системы.

### 2.5.4 Indicators (Признаки проявления)

| Параметр | Пороговое значение | Источник данных |
|----------|--------------------|-----------------|
| Время отклика API при 10+ запросах | >500 мс | JMeter, Prometheus + Grafana |
| Загрузка страниц каталога sleeves | >3 сек | Lighthouse, Playwright |
| Рост потребления памяти/CPU без увеличения нагрузки | >20% | Prometheus + Grafana, docker stats |

### 2.5.5 Mitigation Strategy (Стратегия смягчения)

1. Кэширование часто запрашиваемых данных (каталог sleeves) через Redis.
2. Оптимизация запросов к БД (индексы, пагинация, N+1 query detection).
3. Нагрузочное тестирование в CI/CD после каждого крупного изменения.

### 2.5.6 Contingency Plan (Стратегия наступления)

1. Вертикальное масштабирование сервера (увеличение ресурсов helios).
2. Добавление реплик чтения БД для разгрузки основной базы.
3. Временное отключение некритичных функций (аналитика, отчёты) под нагрузкой.

## 2.6 R6: Зависимость от внешних API и поставщиков

### 2.6.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Средняя. Серьёзность: Высокая. Тип риска: Технологический. Порог: отказ API поставщика > 4 часов.

SCMS зависит от внешних API: генетические архивы (данные о клонированных телах), Google OAuth (регистрация клиентов). Срыв работы этих API или изменение формата ответов может парализовать часть функционала.

### 2.6.2 Description (Описание)

Внешние API (генетические архивы, Google OAuth) могут быть недоступны, изменить формат данных или ввести ограничения скорости. Это влияет на интеграционные модули SCMS и может привести к остановке критических процессов.

### 2.6.3 Impacts (Влияние)

- Невозможность получения данных о доступных sleeves (остановка подбора тела).
- Нарушение регистрации клиентов через Google OAuth.
- Необходимость экстренной доработки интеграционного слоя.

### 2.6.4 Indicators (Признаки проявления)

| Параметр | Пороговое значение | Источник данных |
|----------|--------------------|-----------------|
| Сбои API генетических архивов | >2 раза в месяц | Мониторинг API, логи интеграции |
| Ошибки OAuth-провайдера | >3 раз в месяц | Auth-логи, Sentry |
| Время ответа внешнего API | >5 сек | Мониторинг интеграции |

### 2.6.5 Mitigation Strategy (Стратегия смягчения)

1. Поддержка интеграции с минимум двумя поставщиками каждого типа.
2. Абстрактный слой интеграции в архитектуре SCMS (легкая смена провайдера).
3. Локальное кэширование критичных данных для автономной работы.
4. Graceful degradation: при недоступности API — показ кэшированных данных с пометкой.

### 2.6.6 Contingency Plan (Стратегия наступления)

1. Экстренный переход на резервного поставщика (переключение API-ключа в SCMS).
2. Использование локального хранилища данных до восстановления основного поставщика.
3. Временный ручной ввод данных при недоступности API (режим офлайн с последующей синхронизацией).

## 2.7 R7: Нестабильность требований заказчика

### 2.7.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Средняя. Серьёзность: Высокая. Тип риска: Процессный. Порог: >5 изменений требований за спринт.

В процессе разработки заказчик может вносить изменения в требования: добавлять новые функции, изменять существующую логику или уточнять ранее неформализованные требования. Эти изменения могут происходить без учёта текущего состояния разработки и без пересмотра сроков.

### 2.7.2 Description (Описание)

Заказчик по мере развития проекта лучше понимает свои потребности и может менять приоритеты. Происходит постепенное расширение требований без корректировки сроков и ресурсов. В результате возникает ситуация нестабильности требований, при которой команда вынуждена постоянно перерабатывать уже реализованный функционал.

### 2.7.3 Impacts (Влияние)

- Увеличение объёма работы, появление повторных задач.
- Снижение скорости разработки, увеличение времени на интеграцию.
- Усложнение тестирования, рост вероятности ошибок.
- Ухудшение качества конечного продукта.

### 2.7.4 Indicators (Признаки проявления)

| Параметр | Пороговое значение | Источник данных |
|----------|--------------------|-----------------|
| Количество изменений требований за спринт | >5 | GitLab Issue Board |
| Задачи, переработанные более 1 раза | >20% от спринта | GitLab Issues |
| Отклонение трудозатрат от оценки | >50% на >2 задачи | GitLab Issue Board, time tracking |

### 2.7.5 Mitigation Strategy (Стратегия смягчения)

1. Зафиксировать базовый набор требований перед началом разработки спринта.
2. Ввести обязательную процедуру запроса на изменение для всех новых требований.
3. Проводить оценку влияния каждого изменения на сроки и трудозатраты перед его принятием.
4. Ограничить внесение изменений в активный спринт, переносить их в backlog.

### 2.7.6 Contingency Plan (Стратегия наступления)

1. Зафиксировать текущую версию требований и временно остановить добавление новых изменений.
2. Провести анализ всех открытых запросов на изменения и определить критические и второстепенные.
3. Перераспределить задачи: оставить только приоритетный функционал.
4. Пересмотреть план разработки (сроки, объем работ, ресурсы).
5. Согласовать с заказчиком новые границы проекта и зафиксировать их документально.

## 2.8 R8: Конфликты при параллельной разработке

### 2.8.1 Risk Magnitude or Ranking (Вероятность и серьезность)

Вероятность: Высокая. Серьёзность: Средняя. Тип риска: Процессный. Порог: >5 merge-конфликтов за спринт.

При параллельной разработке разные разработчики могут изменять одни и те же файлы или участки кода. При попытке объединения изменений система контроля версий не может автоматически их совместить, и возникает merge conflict.

### 2.8.2 Description (Описание)

2 разработчика работают параллельно над одной кодовой базой, создавая отдельные ветки. При объединении изменений (merge) могут возникать конфликты, если изменения затрагивают одни и те же части кода. Разрешение конфликтов требует ручного вмешательства и занимает значительное время.

### 2.8.3 Impacts (Влияние)

- Увеличение времени интеграции изменений.
- Задержки выполнения задач, снижение пропускной способности команды.
- Риск ошибок при неправильном разрешении конфликтов.
- Увеличение нагрузки на разработчиков.

### 2.8.4 Indicators (Признаки проявления)

| Параметр | Пороговое значение | Источник данных |
|----------|--------------------|-----------------|
| Merge-конфликты за спринт | >5 | GitLab merge requests |
| Время разрешения конфликтов | >2 часов в неделю | Time tracking |
| Ошибки после merge | >2 в спринте | GitLab Issues, CI/CD pipeline |

### 2.8.5 Mitigation Strategy (Стратегия смягчения)

1. Делить задачи так, чтобы разные разработчики работали с независимыми модулями.
2. Ограничивать время жизни feature-веток (частые merge в основную ветку).
3. Внедрить практику регулярной синхронизации веток (ежедневный pull/merge).
4. Использовать code review для выявления потенциальных конфликтов заранее.

### 2.8.6 Contingency Plan (Стратегия наступления)

1. Зафиксировать проблемные участки кода, где возникает наибольшее количество конфликтов.
2. Приостановить параллельную разработку в этих модулях.
3. Назначить ответственного разработчика за интеграцию изменений.
4. Последовательно объединить ветки с ручной проверкой корректности.
5. Провести дополнительное тестирование после разрешения конфликтов.
