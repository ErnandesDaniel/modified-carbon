# 3. Architectural Goals and Constraints (Цели и ограничения)

**Архитектурно-значимые факторы:**

1. **Изоляция сети:** Внутренний портал работает только в изолированном защищённом сегменте (доступ по VPN-каналу клиники). Внешний портал доступен через защищённый HTTPS.
2. **Отказоустойчивость:** Процедура needlecast не должна прерываться. Система должна обеспечивать 100% доступность во время активных процедур.
3. **Масштабируемость:** Монолитная архитектура с кэшированием и оптимизацией запросов. Цель: поддержка до 50 одновременных пользователей.

# 4. Use-Case View (Прецеденты)

Прецеденты системы описаны в спецификации SRS (раздел 2.1) и детализированы в Use Case Specification.

## 4.1 Use-Case Realizations (Реализации прецедентов)

Ниже описаны ключевые архитектурно-значимые прецеденты и их реализация на уровне компонентов системы.

### UC-01: OrderSleeve (Заказ тела клиентом)

**Акторы:** Meth, Sleeve Broker. **Цель:** Просмотр каталога, заказ тела, обработка заказа брокером, отслеживание статуса.

**Реализация:**
- Frontend: `mfe-client-portal` (React) — каталог sleeves с фильтрами, форма заказа, таймлайн кейса.
- Backend: модуль `sleeve` (Spring Boot) — REST API для каталога, резервирования, управления культивированием.
- Модуль `notification` — отправка уведомлений Meth об изменении статуса кейса.

### UC-02: ManageSleeveReserve (Пополнение резерва тел)

**Актор:** Sleeve Broker. **Цель:** Заказ культивирования, приёмка тела.

**Реализация:**
- Frontend: `mfe-staff-portal` (React) — каталог sleeves со статусами, формы заказа и приёмки.
- Backend: модуль `sleeve` — CRUD-операции, интеграция с внешним API генетических архивов (REST).
- Модуль `notification` — уведомления Broker и Meth при изменении статуса культивирования.

### UC-03: ConductNeedlecast (Проведение needlecast)

**Актор:** Needlecaster. **Цель:** Фиксация этапов переноса, мониторинг DHF в реальном времени.

**Реализация:**
- Frontend: `mfe-staff-portal` — интерфейс Needlecaster с дашбордом активной процедуры, поддержка жестового управления.
- Backend: модуль `procedure` — WebSocket (STOMP) для мониторинга в реальном времени (задержка ≤100 мс).
- Модуль `stack` — фиксация перемещений стеков, запись в audit-log.
- Модуль `notification` — уведомления об изменении статуса кейса.

### UC-04: ExamineAndCertify (Осмотр и сертификация)

**Актор:** Psychosurgeon. **Цель:** Постпроцедурное наблюдение, подтверждение или фиксация осложнений, генерация сертификата.

**Реализация:**
- Frontend: `mfe-staff-portal` — медицинские формы, чеклисты валидации, кнопки «Подтвердить» / «Зафиксировать осложнение».
- Backend: модуль `validation` — фиксация результатов осмотра (24ч/48ч/72ч), генерация PDF-сертификата с QR-кодом.
- Модуль `user` — RBAC: доступ только для Psychosurgeon.
- При осложнениях: модуль `procedure` создаёт инцидент, блокирует выпуск клиента.

### UC-05: RegisterMeth (Регистрация Meth)

**Актор:** Meth (новый клиент). **Цель:** Регистрация через внешний портал, создание учётной записи.

**Реализация:**
- Frontend: `mfe-client-portal` — публичная страница с кнопкой «Войти через Google».
- Backend: модуль `user` — интеграция с Google OAuth, создание учётной записи, настройка RBAC (роль Meth).
- Модуль `client` — создание личного кабинета, привязка NDA.

# 5. Logical View (Логическое представление)

## 5.1 Overview (Обзор)

Система разделена на 3 логических слоя: Presentation (React), Business Logic (Java/Spring Boot монолит), Data Layer (PostgreSQL).

## 5.2 Architecturally Significant Design Packages (Значимые пакеты)

**Backend (Java, Spring Boot) — монолитное приложение:**

- `scms-backend` — единое приложение с модулями:
  - `sleeve` — учёт инвентаря, культивирование, резервирование, мед. карты
  - `stack` — реестр стеков, история перемещений, audit-log
  - `procedure` — мониторинг needlecast, тестирование, таймеры
  - `validation` — постпроцедурное наблюдение, сертификация (PDF)
  - `user` — аутентификация, RBAC, управление пользователями
  - `client` — онбординг, контракты, документы, профили Meth
  - `notification` — отправка уведомлений (email/SMS/bell icon)
  - `reporting` — генерация отчётов, поиск, экспорт PDF/Excel

**Frontend (React):**

- `mfe-client-portal` — внешний портал для Meth (минималистичный UI).
- `mfe-staff-portal` — внутренний портал для персонала (три интерфейса: Broker, Needlecaster, Psychosurgeon, Admin).
- `shared-ui-kit` — общие компоненты (таблицы, формы, дашборды, индикаторы статусов).

# 6. Process View (Процессное представление)

**Потоки выполнения:**

1. **Пользовательские запросы (синхронные):** REST API (Spring MVC) — поиск, просмотр, редактирование данных. Таймаут: 5 секунд.
2. **Мониторинг needlecast (асинхронный):** WebSocket (STOMP). Backend публикует обновления каждые 100 мс. Frontend подписывается через WebSocket.
3. **Автоматические процессы (фоновые задачи):**
   - Auto-release reservation: Scheduled task, каждые 60 минут проверяет просроченные резервирования.
   - Notification dispatch: Внутренний планировщик задач (Spring @Scheduled) обрабатывает очередь уведомлений.
   - Certificate generation: Асинхронная генерация PDF после успешной валидации.
4. **Аудит-лог (синхронная запись):** Audit-лог записывается в БД и дублируется в отдельный файл на диске (неизменяемость).

# 7. Deployment View (Развёртывание)

Production-система развёртывается на одном выделенном облачном сервере (VPS) с использованием Docker Compose: Backend — контейнер-монолит, PostgreSQL — отдельный контейнер, Nginx — reverse proxy, терминация TLS. Для разработки и тестирования используется учебный сервер helios.cs.ifmo.ru (FreeBSD 14.4-STABLE).

**Сетевые интерфейсы:**
- Port 443 (HTTPS) — внешний портал для Meth (доступ из интернета).
- Port 8443 (HTTPS) — внутренний портал (доступ только по защищённому VPN-каналу клиники).

# 9. Size and Performance (Размер и производительность)

- Среднее время отклика API: ≤300 мс (95 перцентиль).
- Задержка WebSocket (мониторинг needlecast): ≤100 мс.
- Генерация PDF сертификата: ≤5 секунд.
- Поиск в каталоге sleeves (50 000 записей): ≤2 секунды.
- Максимальное количество одновременных пользователей: 150 сессий.
- Потребление памяти (пик): ≤16 ГБ.
- Размер БД (архив 1 год): ~500 ГБ.

# 10. Quality (Качество)

Архитектура удовлетворяет следующим атрибутам качества:

- **Надёжность:** Автоматический перезапуск Docker при отказе. Данные DHF дублируются в реальном времени. Audit-лог с однократной записью (append-only).
- **Безопасность:** Квантовое шифрование данных стеков. 2FA для Meth. RBAC на уровне backend. Audit-log с однократной записью (append-only).
- **Масштабируемость:** Вертикальное масштабирование с кэшированием часто запрашиваемых данных (Redis).
- **Модифицируемость:** Модульная структура монолита позволяет изменять/добавлять модули с изоляцией через чёткие интерфейсы слоёв.
